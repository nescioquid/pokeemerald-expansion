# How to make an Expansion version

_If you need instructions on how to release a new Expansion version, check out the enclosed instruction book. --@**AsparagusEduardo**_

> [!NOTE]
> _This process requires write access to the repo._

### Autogenerating a changelog for the `master` branch

If the changelog you're making is for a minor version (such as 1.13.0), make sure to sync the `upcoming` branch with `master` before starting. Keep in mind that if there are unreleased changes in `master`, they should be made into a patch version released alongside the minor version.

1. Go to https://github.com/rh-hideout/pokeemerald-expansion/releases.

2. Press the option "Draft a new release".

3. Fill in the following fields:

   - In "Choose a tag", write the name of the tag for the desired release number (so for version 1.2.3, you'd write `expansion/1.2.3`). **It cannot be an existing tag**.

   - In "Target", choose `master`.

   - In "Previous tag", select the latest version released.

4. Press "Generate release notes". This will fill the description with a list of pull requests made to the `master` branch since the lastest release.

5. You should copy the contents to your text editor of choice for [sorting them in the changelog](#sorting-prs-in-the-changelog).

6. If the changelog you're making is for a minor version (such as 1.13.0), **don't close the current window** and follow the next steps below to [do the same thing for the upcoming branch](#for-minor-releases-autogenerating-a-changelog-for-the-upcoming-branch). Otherwise, go straight to [sorting them](#sorting-prs-in-the-changelog).

#### _For minor releases:_ Autogenerating a changelog for the `upcoming` branch

1. Delete the text and title generated in the site.

2. Change "Target" to `upcoming`.

3. Press "Generate release notes". This will autogenerate the description with changes from both branches, as they've been merged.

4. Use a comparison tool to remove any shared pull requests from `master`.

   - Also remove any shared "New Contributor" entries.

5. You should now have a text that only contains pull requests made to `upcoming`.

> [!TIP]
> _You can check out [WinMerge](https://winmerge.org/) to make comparing these files easier on Windows._

### Sorting pull requests in the changelog

1. Copy the `docs/changelogs/template.md` file into a new file with the corresponding version for file and folder (so for version 1.2.3, you'd copy the file into `docs/changelogs/1.2.x/1.2.3.md`).

2. Use the following Regex to adapt all pull request links into the format currently used:

   - Search

     ```console
     in https://github\.com/rh-hideout/pokeemerald-expansion/pull/(\d+)
     ```

   - Replace

     ```console
     in [#$1](https://github.com/rh-hideout/pokeemerald-expansion/pull/$1)
     ```

3. At the bottom of the template, replace the `"\_**\_"` in `<!--Last pull request: \_\_**-->` with the number of the last pull request in your autogenerated changelog. This will help you keep track of any new pull requests that are merged in before you're finished with your changelog.

4. Sort the pull requests by the categories present in the pull request taking the following considerations:

   - Keep the language of the changelog as newbie friendly as possible, explaining how the pull request affects them.

   - The format of the main line is as follows:

     ```
     {{Description of the change}} by @{{GitHub user}} in {{pull request link}}
     ```

   - If a pull request reverts a previous pull request, both should be removed.

     - If the reverted pull request's contents are then re-added it should be treated as if it's the first time added, with all the proper documentation needed.

   - If a pull request's content fits into multiple categories, like fixing two unrelated Ability and Move effects, you may duplicate the pull request line and put it in both categories, changing the description of it accordingly.

   - When refering to an element present in the code, always enclose them with `backticks` <`> to easily tell them apart, such as:

     - "Converted `settotemboost` command to `callnative`."
     - "Changed `MOVEEND_` defines to an enum."

   - A pull request's technical changes that may conflict with user changes should have an entry in the "Refactors" section at the beginning of the changelog. Any of these changes that requires a migration script should also be marked as such by appending the corresponding emoji listed there. The section should include, but it's not limited to:

     - Massive data format and/or structuring changes.
     - Converting defines to enums.
     - Renaming structs and/or their fields.
     - Removing enums/defines/structs.

   - For fixes:

     - Once on their respective categories, if a pull request fixes multiple issues at once in that category, you may make a sublist of those issues to properly detail each one and avoid just writing "Fixed multiple ability issues" or an overly verbose sentence for the pull request.
     - Try to fit the contents of a pull request as a single sentence in the past tense.
     - **Do not write** something like "Fixed Parental Bond", as this doesn't explain _what_ was fixed in Parental Bond. Instead, write something like "Fixed Parental Bond not affecting Snore".

   - For new configs:

     - Add the name of the config as part of the sentence, with subitems explaining what they do based on their generation if it's a generational config, like:

       ```
       - Added missing `B_AFTER_YOU_TURN_ORDER` config by @PhallenTree in [#5400](https://github.com/rh-hideout/pokeemerald-expansion/pull/5400)
           - Gen 5-7: After You fails if the order remains the same after using After You.
           - Gen 8+: After You no longer fails if the turn order remains the same after using After You.
       ```

   - For other new features:
     - Explain how to use the feature completely, listing all its features as needed. For now, this is the only source of documentation for these features, so it's important to be thorough.

### Preparing the code for the new version

1. Search for all non-changelog instances of the previous released version and update them to the newer version. As of writing, it's these files:

  - `README.md`:

    ```diff
    - Based off RHH's pokeemerald-expansion 1.2.2 https://github.com/rh-hideout/pokeemerald-expansion/
    + Based off RHH's pokeemerald-expansion 1.2.3 https://github.com/rh-hideout/pokeemerald-expansion/
    ```
    
    ```diff
    - - Once you have your remote set up, run the command `git pull RHH expansion/X.Y.Z`, replacing X, Y and Z with the digits of the respective version you want to update to (eg, to update to 1.2.2, use `git pull RHH expansion/1.2.2`).
    + - Once you have your remote set up, run the command `git pull RHH expansion/X.Y.Z`, replacing X, Y and Z with the digits of the respective version you want to update to (eg, to update to 1.2.3, use `git pull RHH expansion/1.2.3`).
    ```

  - `.github/ISSUE_TEMPLATE/*.yaml`
    
    - Patch version:
    
      ```diff
      options:
      -   1.2.2 (Latest release)
      +   1.2.3 (Latest release)
          master (default, unreleased bugfixes)
          upcoming (Edge)
      +   1.2.2
          1.2.1
          1.2.0
      ```
    
    - Minor Version:
    
      ```diff
      options:
      -   1.2.2 (Latest release)
      +   1.2.3 (Latest release)
          master (default, unreleased bugfixes)
          upcoming (Edge)
      +   1.2.2
          1.2.1
          1.2.0
      -   1.1.6
      -   1.1.5
      -   1.1.4
      -   1.1.3
      -   1.1.2
      -   1.1.1
      -   1.1.0
      -   pre-1.1.0
      +   pre-1.2.0
      ```
  
  - `docs/SUMMARY.md`:
    
    - Patch version:
    
      ```diff
      [Changelog](./CHANGELOG.md)
          - [1.2.x]()
      +       - [Version 1.2.3](changelogs/1.2.x/1.2.3.md)
              - [Version 1.2.2](changelogs/1.2.x/1.2.2.md)
              - [Version 1.2.1](changelogs/1.2.x/1.2.1.md)
              - [Version 1.2.0](changelogs/1.2.x/1.2.0.md)
      ```
    
    - Minor version:
    
      ```diff
      [Changelog](./CHANGELOG.md)
      +   - [1.3.x]()
      +       - [Version 1.3.0](changelogs/1.3.x/1.3.0.md)
          - [1.2.x]()
              - [Version 1.2.2](changelogs/1.2.x/1.2.2.md)
              - [Version 1.2.1](changelogs/1.2.x/1.2.1.md)
              - [Version 1.2.0](changelogs/1.2.x/1.2.0.md)
      ```
 
  - `include/constants/expansion.h`:

    - The defines should already have the version we're targetting as part of the previous changelog process.

      ```diff
      - // Last version: 1.2.1
      + // Last version: 1.2.2
        #define EXPANSION_VERSION_MAJOR 1
        #define EXPANSION_VERSION_MINOR 2
      - #define EXPANSION_VERSION_PATCH 2
      + #define EXPANSION_VERSION_PATCH 3

      // FALSE if this this version of Expansion is not a tagged commit, i.e.
      // it contains unreleased changes.
      - #define EXPANSION_TAGGED_RELEASE FALSE
      + #define EXPANSION_TAGGED_RELEASE TRUE
      ```

### Make a pull request with the changes

Provide all the changes from [Sorting pull requests in the changelog](#sorting-prs-in-the-changelog) and [Preparing the code for the new version](#preparing-the-code-for-the-new-version).

Also post the changelog itself for feedback from contributors and maintainers.

Once all feedback has been addressed, you may merge.

### Create the release on GitHub

1. Copy the contents of your manual changelog into the description of your release.

2. Modify the title to "Version X.Y.Z", such as "Version 1.2.3".

3. Be sure to have the "Set as the latest release" option set, then press "Publish Release".

This creates a new tag in the repo that users can pull from like they can with branches.

### Post-release handling

1. **Don't accept any new pull requests yet**! We have to prepare for the next cycle first.

2. Go to `include/constants/expansion.h` and merge the following changes to the repo (pull request or direct commit, doesn't matter much) for patch versions:

  ```diff
  - // Last version: 1.2.2
  + // Last version: 1.2.3
    #define EXPANSION_VERSION_MAJOR 1
    #define EXPANSION_VERSION_MINOR 2
  - #define EXPANSION_VERSION_PATCH 3
  + #define EXPANSION_VERSION_PATCH 4

    // FALSE if this this version of Expansion is not a tagged commit, i.e.
    // it contains unreleased changes.
  - #define EXPANSION_TAGGED_RELEASE TRUE
  + #define EXPANSION_TAGGED_RELEASE FALSE
  ```

With this, the repo is ready again to receive new pull requests.
